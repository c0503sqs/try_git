# gh pr

## 能学到什么

- 用命令行开 PR、查看、检出、review、合并
- `--fill`、`--draft`、`--auto` 的实际用途
- 从 fork 发 PR 的写法
- 合并策略与分支清理

## 创建 PR

```bash
gh pr create --base main --title "feat(search): 支持按标签过滤" --body "## 做了什么

- 新增 tag 过滤参数
- 补充测试

Closes #42"
```

常用参数：

| 参数 | 作用 |
| --- | --- |
| `-B, --base` | 目标分支，默认仓库默认分支 |
| `-H, --head` | 源分支，fork 场景写 `user:branch` |
| `-t, --title` | 标题 |
| `-b, --body` | 正文 |
| `-F, --body-file` | 从文件读正文 |
| `-f, --fill` | 用提交信息自动填标题和正文 |
| `-d, --draft` | 草稿 PR |
| `-w, --web` | 在浏览器里创建 |
| `-l, --label` | 加标签 |
| `-a, --assignee` | 指派 |
| `-r, --reviewer` | 请求 review |

`--fill` 适合单提交 PR；多提交时正文会变成提交列表，通常不如手写。

草稿转正式：

```bash
gh pr ready
gh pr ready 123
```

## 查询

```bash
gh pr list
gh pr list --state open --author @me
gh pr list --search "review-requested:@me"
gh pr view 123
gh pr view 123 --web
gh pr view 123 --json number,title,state,mergeable,reviewDecision
gh pr diff 123
gh pr checks 123
gh pr status
```

`gh pr status` 汇总三类 PR：你创建的、请求你 review 的、你参与过的。

`gh pr checks` 看 CI：

```text
All checks were successful
0 failing, 3 successful, 0 skipped, and 0 pending checks

✓  build   1m2s
✓  test    2m18s
✓  lint    12s
```

## 检出别人的 PR

```bash
gh pr checkout 123
```

它会自动 fetch 对应分支并切换。审查别人的代码时比手动找 fork 方便得多。

## Review

```bash
gh pr review 123 --approve
gh pr review 123 --approve --body "LGTM"
gh pr review 123 --comment --body "这里可以简化"
gh pr review 123 --request-changes --body "需要补充测试"
```

在 PR 里回复评论暂时还是要用网页；`gh pr comment 123 --body "..."` 可以发普通评论。

## 合并

```bash
gh pr merge 123 --squash --delete-branch
gh pr merge 123 --merge --delete-branch
gh pr merge 123 --rebase --delete-branch
```

| 参数 | 结果 |
| --- | --- |
| `--squash` | 所有提交压成一个，主分支历史干净 |
| `--merge` | 生成合并提交，保留分支结构 |
| `--rebase` | 提交逐个放到主分支后，无合并提交 |
| `--delete-branch` | 合并后删除本地和远端分支 |
| `--auto` | 开启自动合并，等检查通过后自动执行 |
| `--admin` | 绕过分支保护（需要管理员权限） |

自动合并：

```bash
gh pr merge 123 --auto --squash
```

适合 PR 已经写得差不多、只等 CI 的情况。

## 更新落后的分支

```bash
gh pr update-branch 123
gh pr update-branch 123 --rebase
```

相当于在服务端把主分支合并进 PR 分支（或 rebase）。省得本地操作再推一次。

## 从 fork 发 PR

```bash
gh pr create \
  --repo owner/upstream-repo \
  --base main \
  --head your-name:fix/typo \
  --title "fix: 更正文档错别字"
```

| 部分 | 含义 |
| --- | --- |
| `--repo owner/upstream-repo` | 目标仓库是上游 |
| `--base main` | 合进上游的 main |
| `--head your-name:fix/typo` | 源是你 fork 里的分支 |

## 关闭与重开

```bash
gh pr close 123
gh pr reopen 123
```

关闭不等于删除，分支和提交都还在。

## 注意事项

1. **PR 必须在有提交的分支上创建**。本地有未推送提交时，`gh pr create` 会问你要推到哪。
2. **`--fill` 依赖提交信息质量**。提交都写「update」时，自动填充的 PR 标题也没法看。
3. **合并方式受仓库设置限制**。只允许 squash 的仓库，`--merge` 会失败。
4. **`--delete-branch` 同时删本地分支**，如果你还在那个分支上，会先切回默认分支。
5. **`gh pr checks` 需要 Actions 或第三方检查已运行**，刚推送时可能显示 pending。
6. **review 评论的精细化操作仍建议用网页**，命令行更适合批准、要求修改、发整体评论。
7. **合并前先同步本地主分支**。网页合并后，本地 `main` 不会自动更新，记得 `git switch main && git pull`。

## 练习

1. 在一个测试仓库里建分支、提交、推送，用 `gh pr create --draft` 开草稿 PR。
2. 用 `gh pr view --json state,mergeable` 查看状态，再用 `gh pr ready` 转正式。
3. 用 `gh pr checks` 查看 CI，用 `gh pr diff` 看改动。
4. 分别用 `--squash` 和 `--rebase` 合并两个测试 PR，对比 `git log --graph`。
